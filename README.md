# Практическая работа: локальный DNS-сервер на Ubuntu Desktop

В этой работе вы создадите две виртуальные машины с Ubuntu Desktop в VMware Workstation и настроите собственный локальный DNS-сервер.

Первая Ubuntu будет DNS-сервером с BIND9. Вторая Ubuntu будет клиентом, который будет использовать этот сервер для разрешения имён.

В локальной сети будет создана собственная DNS-зона:

~~~text
pgk.test
~~~

После настройки клиент сможет обращаться к компьютерам по именам. Например, если VMware выдаст серверу адрес `192.168.100.128`, а клиенту `192.168.100.129`:

~~~text
dns.pgk.test    → 192.168.100.128
client.pgk.test → 192.168.100.129
~~~

При этом обычные домены из интернета тоже должны продолжить работать:

~~~text
yandex.ru
ubuntu.com
github.com
~~~

В конце работы вы специально сломаете DNS, а затем определите причину неисправности по симптомам.

> Адреса `192.168.100.128` и `192.168.100.129` используются только как пример. VMware может выдать другие адреса. В работе нужно использовать реальные IP-адреса своих виртуальных машин.

## Что мы создаём

Для работы нужны две виртуальные машины. У каждой будет **один сетевой адаптер в режиме NAT**.

~~~text
                         Интернет
                            │
                            │
                     VMware NAT
                       VMnet8
                            │
              ┌─────────────┴─────────────┐
              │                           │
              ▼                           ▼
┌────────────────────────┐   ┌────────────────────────┐
│ Ubuntu Desktop №1      │   │ Ubuntu Desktop №2      │
│ DNS-сервер             │   │ DNS-клиент             │
│                        │   │                        │
│ BIND9                  │   │ DNS: адрес сервера     │
│ dns.pgk.test           │   │ client.pgk.test        │
└────────────────────────┘   └────────────────────────┘
~~~

Обе виртуальные машины находятся в одной NAT-сети VMware. Поэтому они:

- получают доступ в интернет;
- получают IP-адреса от DHCP VMware;
- могут обращаться друг к другу по этим IP-адресам.

Для этой работы **не нужен второй NAT адаптер** и не нужно открывать **Virtual Network Editor**.

Это важно для учебных компьютеров: добавление сетей VMware или изменение VMnet может потребовать пароль администратора Windows. В этой работе такие права не нужны.

DNS-сервер будет знать локальные имена из зоны **pgk.test**.

Если клиент спросит адрес **dns.pgk.test**, BIND9 ответит сам.

Если клиент спросит адрес **yandex.ru**, BIND9 передаст запрос внешнему DNS-серверу и вернёт клиенту полученный ответ.

## Что такое DNS

DNS — система доменных имён.

Её основная задача — преобразовать удобное человеку имя в IP-адрес.

Например:

~~~text
yandex.ru → 77.88.55.88
~~~

IP-адрес нужен сети для подключения к нужному компьютеру, но человеку удобнее запоминать имя.

Без DNS пользователю пришлось бы запоминать адреса:

~~~text
192.168.100.128
192.168.100.129
77.88.55.88
~~~

С DNS можно использовать имена:

~~~text
dns.pgk.test
client.pgk.test
yandex.ru
~~~

DNS можно сравнить с телефонной книгой:

~~~text
Имя компьютера → DNS → IP-адрес
~~~

Важно понимать: DNS не выполняет само подключение к серверу. Он только помогает узнать IP-адрес.

После получения IP-адреса клиент уже самостоятельно подключается к нужному сервису.

## Как работает DNS-запрос

Когда клиент выполняет:

~~~bash
ping dns.pgk.test
~~~

происходит примерно следующее:

~~~text
Ubuntu-клиент
     │
     │ Какой IP у dns.pgk.test?
     ▼
DNS-сервер 192.168.100.128
     │
     │ Запись найдена в зоне pgk.test
     ▼
Ответ: 192.168.100.128
     │
     ▼
Ubuntu-клиент отправляет ping на 192.168.100.128
~~~

Для обычного интернет-домена схема немного другая:

~~~text
Ubuntu-клиент
     │
     │ Какой IP у yandex.ru?
     ▼
Наш BIND9
     │
     │ Локальной записи нет
     ▼
Внешний DNS-сервер
     │
     │ Возвращает настоящий IP
     ▼
Наш BIND9
     │
     ▼
Ubuntu-клиент
~~~

Таким образом, клиенту достаточно знать адрес только одного DNS-сервера — нашего.

## Какие DNS-серверы бывают

В реальных сетях DNS-сервер может выполнять разные роли.

### Авторитетный DNS-сервер

Хранит DNS-записи определённой зоны и знает правильные ответы для неё.

В этой работе BIND9 будет авторитетным сервером для:

~~~text
pgk.test
~~~

### Рекурсивный DNS-сервер

Ищет ответ для клиента, если сам его не знает.

В этой работе BIND9 сможет получать ответы для обычных интернет-доменов.

### DNS-forwarder

Передаёт неизвестные запросы другому DNS-серверу.

Мы настроим BIND9 так, чтобы запросы к внешним доменам передавались на публичные DNS-серверы.

### Кэширующий DNS-сервер

Запоминает полученные ответы на некоторое время.

Если несколько клиентов часто запрашивают один и тот же домен, DNS-серверу не обязательно каждый раз выполнять полный запрос заново.

В этой работе один BIND9 будет одновременно:

- авторитетным сервером для **pgk.test**;
- рекурсивным сервером для клиентов нашей локальной сети;
- forwarder для внешних запросов;
- DNS-кэшем.

## Основные типы DNS-записей

DNS умеет хранить разные виды информации.

| Тип | Назначение | Пример |
| --- | --- | --- |
| A | Имя → IPv4-адрес | dns.pgk.test → 192.168.100.128 |
| AAAA | Имя → IPv6-адрес | host.example → IPv6 |
| CNAME | Псевдоним другого имени | www → server |
| MX | Почтовый сервер домена | mail.example |
| NS | DNS-сервер зоны | dns.pgk.test |
| PTR | IP-адрес → имя | 192.168.100.128 → dns.pgk.test |

В основной части работы будут использоваться записи **A** и **NS**.

## Почему используется зона pgk.test

Для учебной сети нужна зона, которая не конфликтует с настоящими доменами в интернете.

Мы будем использовать:

~~~text
pgk.test
~~~

Зона **.test** специально предназначена для примеров, тестирования и локальных лабораторных работ.

Не используйте для этой работы зону **.local**.

В Linux и других операционных системах **.local** часто используется протоколом mDNS. Из-за этого запросы могут обрабатываться не обычным DNS, а отдельным механизмом поиска устройств в локальной сети.

Поэтому для лабораторной работы безопаснее использовать:

~~~text
pgk.test
~~~


## Шаг 1. Проверьте режим NAT

В этой работе обе виртуальные машины будут использовать стандартную сеть VMware **NAT**.

Никакие дополнительные сети создавать не нужно.

При создании каждой виртуальной машины убедитесь, что её сетевой адаптер работает в режиме:

~~~text
NAT
~~~

Обычно VMware выбирает NAT автоматически.

Режим NAT одновременно решает две задачи:

- виртуальная машина получает доступ в интернет;
- виртуальные машины в одной NAT-сети VMware могут обращаться друг к другу.

> Не открывайте **Virtual Network Editor** и не добавляйте NAT адаптер. Для этой практической это не требуется.

## Шаг 2. Создайте DNS-сервер

Создайте первую виртуальную машину с Ubuntu Desktop.

Рекомендуемые параметры:

| Параметр | Значение |
| --- | --- |
| Имя | Ubuntu DNS Server |
| Операционная система | Ubuntu Desktop |
| Оперативная память | 2–4 ГБ |
| Процессор | 2 ядра |
| Диск | от 20 ГБ |
| Сетевой адаптер 1 | NAT |

Установите Ubuntu Desktop обычным способом.

После установки войдите в систему.

### Важно: отключите установочный ISO

После первого успешного запуска установленной Ubuntu выключите виртуальную машину:

~~~bash
sudo poweroff
~~~

В VMware откройте **VM → Settings → CD/DVD**.

Снимите флажок **Connect at power on** или выберите отключение ISO-образа.

Это нужно сделать, чтобы при следующем запуске снова не открылся установщик Ubuntu.

После этого запустите виртуальную машину снова.

Откройте терминал сочетанием:

~~~text
Ctrl + Alt + T
~~~

Проверьте имя компьютера:

~~~bash
hostname
~~~

Установите удобное имя DNS-сервера:

~~~bash
sudo hostnamectl set-hostname dns-server
~~~

После повторного входа или перезагрузки новое имя будет отображаться в терминале.

## Шаг 3. Создайте DNS-клиент

Создайте вторую виртуальную машину с Ubuntu Desktop.

Рекомендуемые параметры такие же:

| Параметр | Значение |
| --- | --- |
| Имя | Ubuntu DNS Client |
| Операционная система | Ubuntu Desktop |
| Оперативная память | 2–4 ГБ |
| Процессор | 2 ядра |
| Диск | от 20 ГБ |
| Сетевой адаптер 1 | NAT |

После установки Ubuntu также отключите установочный ISO:

1. Выключите виртуальную машину.
2. Откройте **VM → Settings → CD/DVD**.
3. Снимите **Connect at power on** или отключите ISO.
4. Запустите Ubuntu снова.

Затем задайте имя компьютера:

~~~bash
sudo hostnamectl set-hostname dns-client
~~~

Теперь у вас должны быть две отдельные виртуальные машины:

~~~text
dns-server
dns-client
~~~


## Шаг 4. Отключите ISO и проверьте сеть

На обеих виртуальных машинах убедитесь, что:

- установочный ISO больше не подключается при запуске;
- используется один сетевой адаптер;
- режим адаптера — **NAT**;
- включён **Connect at power on** для сетевого адаптера.

Добавлять второй сетевой адаптер не нужно.

После запуска Ubuntu выполните на каждой машине:

~~~bash
ip -br address
~~~

Пример:

~~~text
lo       UNKNOWN  127.0.0.1/8
ens33    UP       192.168.100.128/24
~~~

IP-адрес вида `192.168.x.x` или другого частного диапазона будет выдан DHCP-сервером VMware.

Названия интерфейсов могут отличаться, например:

~~~text
ens33
ens160
enp2s0
~~~

Это нормально.


## Шаг 5. Узнайте IP-адреса и подсеть

На DNS-сервере выполните:

~~~bash
ip -br address
ip route
~~~

Запишите:

- IP-адрес DNS-сервера;
- маску сети;
- адрес сети.

Пример:

~~~text
IP DNS-сервера: 192.168.100.128
Сеть:            192.168.100.0/24
~~~

На DNS-клиенте выполните:

~~~bash
ip -br address
~~~

Запишите его адрес.

Например:

~~~text
IP DNS-клиента: 192.168.100.129
~~~

Адреса выдаёт DHCP VMware, поэтому на разных компьютерах они могут отличаться.

Во всех следующих командах:

- `192.168.100.128` — пример IP DNS-сервера;
- `192.168.100.129` — пример IP клиента;
- `192.168.100.0/24` — пример NAT-подсети.

Если у вас другие значения, подставляйте свои.

Для этой практической вручную назначать статические IP не нужно. Важно лишь использовать текущий адрес DNS-сервера во всех настройках клиента.

> Если после перезапуска VMware адрес DNS-сервера изменился, узнайте новый адрес командой `ip -br address` и обновите его в настройках DNS клиента.

## Шаг 6. Проверьте сеть до настройки DNS

Сначала убедитесь, что обычная IP-сеть работает.

На клиенте выполните:

~~~bash
ping -c 4 192.168.100.128
~~~

Должны приходить ответы.

На сервере выполните:

~~~bash
ping -c 4 192.168.100.129
~~~

Проверьте интернет на обеих машинах:

~~~bash
ping -c 4 8.8.8.8
~~~

Затем проверьте существующий DNS:

~~~bash
ping -c 4 ubuntu.com
~~~

На этом этапе локальные имена ещё работать не должны:

~~~bash
ping -c 2 dns.pgk.test
~~~

Скорее всего, будет ошибка разрешения имени.

Это нормально: свой DNS мы ещё не настроили.

## Шаг 7. Установите BIND9

Все следующие команды до отдельного указания выполняются на машине **dns-server**.

Обновите информацию о пакетах:

~~~bash
sudo apt update
~~~

Установите BIND9 и утилиты диагностики DNS:

~~~bash
sudo apt install bind9 bind9-utils dnsutils -y
~~~

Запустите DNS-сервер и включите автоматический запуск:

~~~bash
sudo systemctl enable --now bind9
~~~

Проверьте состояние:

~~~bash
systemctl status bind9
~~~

В состоянии должно быть:

~~~text
active (running)
~~~

Нажмите **Q**, чтобы выйти из просмотра.

Проверьте, слушает ли DNS порт 53:

~~~bash
sudo ss -lntup | grep :53
~~~

DNS использует порт:

~~~text
53/UDP
53/TCP
~~~

UDP используется для большинства обычных DNS-запросов.

TCP также является частью DNS и используется, например, когда ответ слишком большой для обычного UDP-запроса.

## Шаг 8. Настройте внешний DNS

Теперь настроим BIND9 так, чтобы он мог разрешать не только нашу локальную зону, но и обычные интернет-домены.

Откройте файл:

~~~bash
sudo nano /etc/bind/named.conf.options
~~~

Приведите блок **options** к следующему виду:

~~~text
options {
    directory "/var/cache/bind";

    recursion yes;

    allow-query {
        localhost;
        192.168.100.0/24;
    };

    allow-recursion {
        localhost;
        192.168.100.0/24;
    };

    listen-on {
        127.0.0.1;
        192.168.100.128;
    };

    listen-on-v6 {
        none;
    };

    forwarders {
        1.1.1.1;
        8.8.8.8;
    };

    dnssec-validation auto;
};
~~~

Сохраните файл:

~~~text
Ctrl + O
Enter
Ctrl + X
~~~

Что означают основные параметры:

| Параметр | Назначение |
| --- | --- |
| recursion yes | Разрешить BIND9 искать ответы для клиентов |
| allow-query | Кто может отправлять DNS-запросы |
| allow-recursion | Кто может использовать рекурсивные запросы |
| listen-on | На каких IPv4-адресах BIND9 слушает порт 53 |
| forwarders | Куда передавать неизвестные внешние запросы |
| dnssec-validation auto | Проверять DNSSEC, когда это возможно |

В этой конфигурации использовать наш DNS смогут только:

- сам сервер;
- устройства из сети **192.168.100.0/24**.

Это важно: открытый рекурсивный DNS-сервер не следует делать доступным всему интернету.

## Шаг 9. Создайте локальную DNS-зону

Откройте файл:

~~~bash
sudo nano /etc/bind/named.conf.local
~~~

Добавьте:

~~~text
zone "pgk.test" {
    type master;
    file "/etc/bind/db.pgk.test";
};
~~~

Сохраните файл.

Что это означает:

| Параметр | Значение |
| --- | --- |
| zone | Имя DNS-зоны |
| pgk.test | Наша локальная зона |
| type master | Этот сервер хранит основную копию зоны |
| file | Файл с DNS-записями |

Теперь BIND9 знает, что он отвечает за зону:

~~~text
pgk.test
~~~

Но самих записей в ней пока нет.

## Шаг 10. Создайте DNS-записи

Создайте файл зоны:

~~~bash
sudo nano /etc/bind/db.pgk.test
~~~

Добавьте:

~~~text
$TTL 86400

@   IN  SOA dns.pgk.test. admin.pgk.test. (
        2026092001
        3600
        1800
        604800
        86400
)

@       IN  NS      dns.pgk.test.

dns     IN  A       192.168.100.128
server  IN  A       192.168.100.128
client  IN  A       192.168.100.129
~~~

Сохраните файл.

Теперь существуют следующие имена:

~~~text
dns.pgk.test    → 192.168.100.128
server.pgk.test → 192.168.100.128
client.pgk.test → 192.168.100.129
~~~

### Что означает SOA

SOA — Start of Authority.

Запись описывает основные параметры DNS-зоны.

Особенно важен Serial:

~~~text
2026092001
~~~

При каждом изменении файла зоны Serial нужно увеличивать.

Удобный формат:

~~~text
ГГГГММДДNN
~~~

Например:

~~~text
2026092001
2026092002
2026092101
~~~

### Почему после имён стоит точка

В файле зоны записано:

~~~text
dns.pgk.test.
~~~

Точка в конце означает, что это полное доменное имя.

Без завершающей точки BIND9 может автоматически добавить имя текущей зоны.

## Шаг 11. Проверьте конфигурацию BIND9

До перезапуска BIND9 обязательно проверьте синтаксис.

Проверьте общую конфигурацию:

~~~bash
sudo named-checkconf
~~~

Если команда ничего не вывела, синтаксис правильный.

Теперь проверьте файл зоны:

~~~bash
sudo named-checkzone pgk.test /etc/bind/db.pgk.test
~~~

Ожидаемый результат похож на:

~~~text
zone pgk.test/IN: loaded serial 2026092001
OK
~~~

Теперь перезапустите BIND9:

~~~bash
sudo systemctl restart bind9
~~~

Проверьте состояние:

~~~bash
systemctl status bind9
~~~

Проверьте порт:

~~~bash
sudo ss -lntup | grep :53
~~~

Среди адресов должен присутствовать:

~~~text
192.168.100.128:53
~~~

## Шаг 12. Разрешите DNS в UFW

Если UFW выключен, DNS может работать и без этого шага. Но в реальной системе входящий доступ лучше контролировать явно.

Разрешите DNS только из нашей учебной сети.

UDP:

~~~bash
sudo ufw allow from 192.168.100.0/24 to any port 53 proto udp
~~~

TCP:

~~~bash
sudo ufw allow from 192.168.100.0/24 to any port 53 proto tcp
~~~

Включите UFW:

~~~bash
sudo ufw enable
~~~

Подтвердите действие.

Проверьте правила:

~~~bash
sudo ufw status
~~~

В правилах должны присутствовать разрешения для порта 53 из сети:

~~~text
192.168.100.0/24
~~~

## Шаг 13. Проверьте DNS напрямую

Теперь перейдите на машину **dns-client**.

Установите утилиты DNS:

~~~bash
sudo apt update
sudo apt install dnsutils -y
~~~

Пока системный DNS клиента ещё не меняем.

Сначала обратимся к нашему серверу напрямую:

~~~bash
dig @192.168.100.128 dns.pgk.test
~~~

В секции ответа должно присутствовать примерно:

~~~text
dns.pgk.test.    86400    IN    A    192.168.100.128
~~~

Проверьте клиента:

~~~bash
dig @192.168.100.128 client.pgk.test
~~~

Ожидаемый адрес:

~~~text
192.168.100.129
~~~

Проверьте сервер:

~~~bash
dig @192.168.100.128 server.pgk.test
~~~

Ожидаемый адрес:

~~~text
192.168.100.128
~~~

Теперь проверьте внешний домен через наш BIND9:

~~~bash
dig @192.168.100.128 yandex.ru
~~~

Если BIND9 настроен правильно, вы получите настоящий IP-адрес yandex.ru.

Это важная проверка.

Она доказывает сразу две вещи:

1. клиент может обратиться к BIND9;
2. BIND9 умеет получать ответы для внешних доменов.

Проверьте также через nslookup:

~~~bash
nslookup dns.pgk.test 192.168.100.128
~~~

## Шаг 14. Укажите собственный DNS на клиенте

До этого мы каждый раз явно указывали сервер:

~~~text
@192.168.100.128
~~~

Теперь настроим Ubuntu так, чтобы она автоматически использовала наш DNS.

На машине **dns-client** откройте:

**Settings → Network**

Откройте настройки NAT-подключения.

На вкладке **IPv4**:

1. адрес оставьте в режиме Automatic (DHCP);
2. отключите автоматическое получение DNS;
3. в поле DNS укажите:

~~~text
192.168.100.128
~~~

Сохраните настройки.

Для NAT подключения также можно указать DNS:

~~~text
192.168.100.128
~~~

Переподключите сетевые интерфейсы или перезагрузите клиент.

Проверьте настройки:

~~~bash
resolvectl status
~~~

В активных соединениях должен присутствовать DNS-сервер:

~~~text
192.168.100.128
~~~

> Ubuntu Desktop обычно использует systemd-resolved. Поэтому в некоторых командах вы можете увидеть локальный адрес 127.0.0.53. Это нормально: приложение отправляет запрос локальному resolver, а тот уже передаёт его DNS-серверу 192.168.100.128.

Можно очистить DNS-кэш клиента:

~~~bash
sudo resolvectl flush-caches
~~~

## Шаг 15. Проверьте локальные имена

Теперь адрес DNS-сервера указывать вручную не нужно.

На клиенте выполните:

~~~bash
ping -c 4 dns.pgk.test
~~~

В начале вывода должен появиться:

~~~text
192.168.100.128
~~~

Проверьте клиента:

~~~bash
ping -c 4 client.pgk.test
~~~

Ожидаемый адрес:

~~~text
192.168.100.129
~~~

Проверьте через dig:

~~~bash
dig dns.pgk.test
~~~

Проверьте через nslookup:

~~~bash
nslookup server.pgk.test
~~~

Если в выводе dig строка **SERVER** содержит:

~~~text
127.0.0.53#53
~~~

это не ошибка.

Запрос сначала попал в локальный systemd-resolved Ubuntu, который затем использовал DNS, указанный в сетевых настройках.

Чтобы полностью обойти локальный resolver и обратиться к BIND9 напрямую, используйте:

~~~bash
dig @192.168.100.128 dns.pgk.test
~~~

## Шаг 16. Проверьте обычные интернет-домены

Проверьте:

~~~bash
ping -c 4 yandex.ru
~~~

Затем:

~~~bash
dig yandex.ru
~~~

Проверьте ещё несколько доменов:

~~~bash
dig ubuntu.com
dig github.com
~~~

Все они должны разрешаться.

Это означает, что переход на собственный DNS не сломал обычный интернет.

Логика теперь выглядит так:

~~~text
dns.pgk.test
    │
    └── BIND9 отвечает сам

yandex.ru
    │
    └── BIND9 → внешний DNS → ответ клиенту
~~~

Проверьте доступ по IP отдельно:

~~~bash
ping -c 4 8.8.8.8
~~~

Если IP работает, но доменное имя нет, проблема почти наверняка связана с DNS.

## Шаг 17. Посмотрите работу DNS-кэша

BIND9 кэширует внешние ответы.

На клиенте выполните прямой запрос:

~~~bash
dig @192.168.100.128 ubuntu.com
~~~

Найдите строку:

~~~text
Query time
~~~

Повторите тот же запрос:

~~~bash
dig @192.168.100.128 ubuntu.com
~~~

Второй ответ часто приходит быстрее, потому что BIND9 уже знает результат.

Время может отличаться на разных компьютерах, поэтому главный смысл этого шага не в конкретном числе миллисекунд, а в понимании механизма:

~~~text
Первый запрос → внешний DNS → BIND9 сохраняет ответ
Следующий запрос → ответ может быть взят из кэша
~~~

В DNS-записях также существует TTL — время, в течение которого запись можно хранить в кэше.

## Шаг 18. Специально сломайте DNS

Теперь проведём диагностику настоящей сетевой проблемы.

### Ситуация 1. Используется чужой DNS

На клиенте временно замените DNS:

~~~text
192.168.100.128
~~~

на:

~~~text
1.1.1.1
~~~

Переподключите сеть и очистите кэш:

~~~bash
sudo resolvectl flush-caches
~~~

Проверьте интернет:

~~~bash
dig yandex.ru
~~~

Он должен работать.

Теперь проверьте локальную зону:

~~~bash
dig dns.pgk.test
~~~

Локальное имя больше не должно разрешаться.

Почему?

Публичный DNS-сервер не знает ничего о вашей локальной зоне **pgk.test**.

При этом сам компьютер по IP всё ещё доступен:

~~~bash
ping -c 4 192.168.100.128
~~~

Получается важный диагностический признак:

~~~text
По IP работает
По локальному имени не работает
→ проверяем DNS
~~~

Верните DNS:

~~~text
192.168.100.128
~~~

### Ситуация 2. DNS-сервер остановлен

На машине **dns-server** остановите BIND9:

~~~bash
sudo systemctl stop bind9
~~~

На клиенте очистите кэш:

~~~bash
sudo resolvectl flush-caches
~~~

Проверьте IP:

~~~bash
ping -c 4 8.8.8.8
~~~

Он должен работать.

Теперь попробуйте:

~~~bash
ping -c 2 yandex.ru
~~~

или:

~~~bash
dig yandex.ru
~~~

DNS-запрос завершится ошибкой или тайм-аутом.

Это показывает, что:

- сеть работает;
- маршрут в интернет работает;
- проблема именно в службе DNS.

Запустите BIND9 снова:

~~~bash
sudo systemctl start bind9
~~~

На клиенте повторите:

~~~bash
dig yandex.ru
dig dns.pgk.test
~~~

Оба запроса должны снова работать.

## Проверка готовой работы

Работа выполнена, если соблюдены все условия:

- созданы две виртуальные машины Ubuntu Desktop;
- обе виртуальные машины используют один сетевой адаптер в режиме NAT;
- записан текущий IP-адрес DNS-сервера, например **192.168.100.128**;
- записан текущий IP-адрес DNS-клиента, например **192.168.100.129**;
- сервер и клиент видят друг друга по IP;
- на сервере установлен и запущен BIND9;
- создана зона **pgk.test**;
- имя **dns.pgk.test** возвращает адрес сервера;
- имя **client.pgk.test** возвращает адрес клиента;
- клиент использует DNS **192.168.100.128**;
- с клиента работают локальные DNS-имена;
- с клиента продолжают разрешаться обычные интернет-домены;
- порт 53 разрешён для локальной сети;
- студент может объяснить разницу между IP-связностью и DNS;
- студент может показать ситуацию, когда IP работает, а имя не работает.

Полезные команды для демонстрации преподавателю.

На сервере:

~~~bash
ip -br address
systemctl status bind9
sudo named-checkconf
sudo named-checkzone pgk.test /etc/bind/db.pgk.test
sudo ss -lntup | grep :53
sudo ufw status
~~~

На клиенте:

~~~bash
ip -br address
resolvectl status
ping -c 2 192.168.100.128
ping -c 2 dns.pgk.test
dig dns.pgk.test
dig @192.168.100.128 client.pgk.test
dig yandex.ru
nslookup server.pgk.test
~~~

## Частые ошибки

### Клиент не видит сервер по IP

Проверьте:

1. Обе виртуальные машины запущены.
2. У обеих используется режим **NAT**.
3. На обеих сетевой адаптер подключён.
4. Вы используете актуальные IP-адреса из команды:

~~~bash
ip -br address
~~~

5. Обе машины получили адреса из одной NAT-сети VMware.

Проверьте маршрут:

~~~bash
ip route
~~~

Если адрес DNS-сервера изменился после перезапуска, используйте новый адрес.

### BIND9 не запускается

Проверьте конфигурацию:

~~~bash
sudo named-checkconf
~~~

Проверьте зону:

~~~bash
sudo named-checkzone pgk.test /etc/bind/db.pgk.test
~~~

Посмотрите журнал:

~~~bash
sudo journalctl -u bind9 --no-pager -n 50
~~~

### Ошибка address already in use на порту 53

Посмотрите, какая программа уже использует порт:

~~~bash
sudo ss -lntup | grep :53
~~~

Обратите внимание, что Ubuntu Desktop может использовать **systemd-resolved** на локальном адресе **127.0.0.53**.

В нашей конфигурации BIND9 явно слушает:

~~~text
127.0.0.1
192.168.100.128
~~~

поэтому он не должен пытаться занять адрес 127.0.0.53.

### Команда dig напрямую работает, а обычный ping по имени нет

Если работает:

~~~bash
dig @192.168.100.128 dns.pgk.test
~~~

но не работает:

~~~bash
ping dns.pgk.test
~~~

значит BIND9 работает, но клиент не использует его как системный DNS.

Проверьте:

~~~bash
resolvectl status
~~~

В настройках должен присутствовать:

~~~text
192.168.100.128
~~~

### Локальные имена работают, а yandex.ru нет

Проверьте интернет с DNS-сервера:

~~~bash
ping -c 4 8.8.8.8
~~~

Проверьте внешний запрос прямо с сервера:

~~~bash
dig @1.1.1.1 yandex.ru
~~~

Проверьте файл:

~~~bash
sudo nano /etc/bind/named.conf.options
~~~

Убедитесь, что указаны forwarders:

~~~text
1.1.1.1
8.8.8.8
~~~

После изменения:

~~~bash
sudo named-checkconf
sudo systemctl restart bind9
~~~

### yandex.ru работает, а pgk.test нет

Проверьте, какой DNS использует клиент:

~~~bash
resolvectl status
~~~

Если клиент использует публичный DNS, например **1.1.1.1**, он не знает локальную зону **pgk.test**.

Верните DNS:

~~~text
192.168.100.128
~~~

### После изменения записи возвращается старый адрес

Увеличьте Serial в файле зоны.

Например:

~~~text
2026092001
~~~

замените на:

~~~text
2026092002
~~~

Проверьте и перезапустите BIND9:

~~~bash
sudo named-checkzone pgk.test /etc/bind/db.pgk.test
sudo systemctl restart bind9
~~~

Очистите кэш клиента:

~~~bash
sudo resolvectl flush-caches
~~~

### В dig отображается SERVER: 127.0.0.53

Для Ubuntu Desktop это нормально.

127.0.0.53 — локальный адрес службы systemd-resolved.

Чтобы увидеть ответ непосредственно от нашего BIND9, выполните:

~~~bash
dig @192.168.100.128 dns.pgk.test
~~~

### Запрос зависает и заканчивается timeout

Проверьте:

~~~bash
systemctl status bind9
~~~

Затем:

~~~bash
sudo ss -lntup | grep :53
~~~

И правила UFW:

~~~bash
sudo ufw status
~~~

Также убедитесь, что сервер доступен:

~~~bash
ping -c 4 192.168.100.128
~~~

## Дополнительное задание

В примере ниже используется учебная NAT-сеть `192.168.100.0/24`. Если VMware выдала вам другую подсеть, имя обратной зоны и PTR-записи будут отличаться.

Основная работа использует прямое разрешение:

~~~text
Имя → IP
~~~

DNS также умеет выполнять обратное разрешение:

~~~text
IP → Имя
~~~

Для этого используются записи PTR и обратные DNS-зоны.

Попробуйте самостоятельно создать обратную зону для сети:

~~~text
192.168.100.0/24
~~~

Имя обратной зоны:

~~~text
100.168.192.in-addr.arpa
~~~

Настройте PTR-записи:

~~~text
192.168.100.128 → dns.pgk.test
192.168.100.129 → client.pgk.test
~~~

После настройки команда:

~~~bash
dig -x 192.168.100.128
~~~

должна вернуть:

~~~text
dns.pgk.test.
~~~

А команда:

~~~bash
dig -x 192.168.100.129
~~~

должна вернуть:

~~~text
client.pgk.test.
~~~

## Что нужно понимать после выполнения

- DNS преобразует доменные имена в IP-адреса.
- DNS обычно использует порт 53 по UDP и TCP.
- A-запись связывает имя с IPv4-адресом.
- NS-запись указывает DNS-сервер зоны.
- PTR-запись используется для обратного разрешения IP в имя.
- Авторитетный DNS-сервер хранит собственные зоны.
- Рекурсивный DNS-сервер получает ответы от других DNS-серверов.
- Forwarder передаёт неизвестные запросы внешнему DNS.
- DNS-кэш позволяет временно хранить уже полученные ответы.
- TTL определяет, как долго DNS-запись может храниться в кэше.
- Локальный DNS позволяет использовать удобные имена внутри организации или домашней сети.
- Собственный DNS не обязан ломать обычные интернет-домены.
- Если IP-адрес доступен, а имя не разрешается, нужно проверять DNS.
- Если не работает даже IP-адрес, проблема находится ниже DNS-уровня.
- Публичный DNS-сервер не знает записи вашей локальной зоны.
- Зону **.test** удобно использовать для учебных лабораторных работ.
- Зону **.local** лучше не использовать для обычного DNS, потому что она часто занята mDNS.
